# Coding Standards

These standards apply to all code generated by this power and should be followed when extending generated projects.

## Kotlin Style

### Naming Conventions

#### Classes and Interfaces
- **PascalCase** for all types
- Interfaces have no `I` prefix
- Implementations append `Impl` only when interface exists

```kotlin
// ✓ Good
interface ItemRepository
class ItemRepositoryImpl : ItemRepository

data class HomeUiState
sealed interface HomeAction

// ✗ Avoid
interface IItemRepository  // No I prefix
class DefaultItemRepository  // Use Impl suffix
```

#### Functions and Properties
- **camelCase** for functions and properties
- Boolean properties start with `is`, `has`, or `can`
- Functions that return Boolean ask a question

```kotlin
// ✓ Good
fun loadItems()
val isLoading: Boolean
val hasError: Boolean
fun canRefresh(): Boolean

// ✗ Avoid
fun LoadItems()  // Wrong case
val loading: Boolean  // Ambiguous
fun refresh(): Boolean  // Not a question
```

#### Constants
- **SCREAMING_SNAKE_CASE** for compile-time constants
- Defined at top level or in `companion object`

```kotlin
// ✓ Good
const val HOME_ROUTE = "home"
const val MAX_RETRY_COUNT = 3

companion object {
    const val DATABASE_NAME = "app-database"
}

// ✗ Avoid
const val homeRoute = "home"  // Wrong case
val HOME_ROUTE = "home"  // Not const
```

#### Files
- File name matches primary class name
- Exception: Extensions can be named by what they extend + suffix
- Multiple small related classes can share a file

```kotlin
// ✓ Good
HomeScreen.kt          // Contains HomeScreen composable
HomeViewModel.kt       // Contains HomeViewModel
ItemMapper.kt         // Contains Item mapping extensions
HomeModels.kt         // Contains HomeUiState + HomeAction

// ✗ Avoid
home_screen.kt        // Wrong case
Screen.kt             // Too generic
```

### Code Organization

#### File Structure Order
1. Package declaration
2. Imports (Android → third-party → java/kotlin → project, alphabetically)
3. Top-level constants
4. Primary class/interface
5. Extension functions
6. Private helper functions

```kotlin
package com.example.app.ui.home

import android.os.Bundle
import androidx.compose.runtime.Composable
import androidx.hilt.navigation.compose.hiltViewModel
import dagger.hilt.android.AndroidEntryPoint
import kotlinx.coroutines.flow.Flow
import com.example.app.core.domain.model.Item

const val HOME_ROUTE = "home"

@Composable
internal fun HomeRoute(...) { }

@Composable
internal fun HomeScreen(...) { }

sealed interface HomeUiState { }

sealed interface HomeAction { }
```

#### Class Member Order
1. `companion object`
2. Properties (abstract → open → override → public → internal → protected → private)
3. Init blocks
4. Constructors (secondary)
5. Functions (abstract → open → override → public → internal → protected → private)
6. Nested classes

### Visibility Modifiers

#### Default to Least Visibility
- Feature module types: `internal` by default
- Core module types: `public` when consumed by features, `internal` otherwise
- Repository implementations: `internal` (interfaces are public)
- DI modules: `internal`

```kotlin
// Feature module
internal class HomeViewModel @Inject constructor(...) { }
internal fun HomeRoute() { }

// Core/domain module (consumed by features)
data class Item(...)  // public, no modifier needed
interface ItemRepository { }  // public

// Core/data module (implementation)
internal class ItemRepositoryImpl : ItemRepository { }
```

#### Never Use `public` Explicitly
Omit `public` modifier; it's the default and adds noise.

```kotlin
// ✓ Good
class SomeClass { }
fun someFunction() { }

// ✗ Avoid
public class SomeClass { }
public fun someFunction() { }
```

### Properties and Functions

#### Use `val` Over `var`
Prefer immutable properties. Use `var` only when mutation is necessary.

```kotlin
// ✓ Good
val items = listOf(1, 2, 3)
val uiState = MutableStateFlow(Loading)

// ✗ Avoid
var items = listOf(1, 2, 3)  // Never reassigned
```

#### Single Expression Functions
Use `=` syntax for single-expression functions.

```kotlin
// ✓ Good
fun double(x: Int) = x * 2
fun isValid(text: String) = text.isNotBlank() && text.length > 3

// ✗ Avoid
fun double(x: Int): Int {
    return x * 2
}
```

#### Named Arguments for Multiple Parameters
Use named arguments when calling functions with 2+ parameters of the same type.

```kotlin
// ✓ Good
stateIn(
    scope = viewModelScope,
    started = WhileSubscribed(5_000),
    initialValue = Loading
)

// ✗ Avoid
stateIn(viewModelScope, WhileSubscribed(5_000), Loading)
```

### Data Classes and Sealed Types

#### Prefer `data class` for Value Objects
Use `data class` when you need structural equality and copy functionality.

```kotlin
// ✓ Good
data class Item(
    val id: String,
    val title: String,
    val description: String
)

// ✗ Avoid
class Item(val id: String, val title: String, val description: String)
```

#### Use Sealed Interfaces for UI State
Model all possible states explicitly with sealed interfaces.

```kotlin
// ✓ Good
sealed interface HomeUiState {
    data object Loading : HomeUiState
    data object Empty : HomeUiState
    data class Success(val items: List<Item>) : HomeUiState
    data class Error(val message: String) : HomeUiState
}

// ✗ Avoid
data class HomeUiState(
    val isLoading: Boolean = false,
    val items: List<Item> = emptyList(),
    val error: String? = null
)  // Can represent invalid states
```

#### Prefer Sealed Interfaces Over Sealed Classes
Sealed interfaces allow data classes to implement multiple sealed hierarchies.

```kotlin
// ✓ Good
sealed interface UiState
data class Success(val data: String) : UiState

// ✗ Avoid (unless inheritance needed)
sealed class UiState
data class Success(val data: String) : UiState()
```

## Compose UI Standards

### Composable Naming
- **PascalCase** (like classes)
- Nouns for screens/components
- No `Composable` suffix

```kotlin
// ✓ Good
@Composable
fun HomeScreen() { }

@Composable
fun ItemCard() { }

// ✗ Avoid
@Composable
fun homeScreen() { }  // Wrong case

@Composable
fun HomeScreenComposable() { }  // Redundant suffix
```

### Composable Parameters

#### Modifier Parameter
- Named `modifier`
- Type `Modifier = Modifier` (default to empty)
- **First optional parameter** (after required params)
- Applied to root layout element

```kotlin
// ✓ Good
@Composable
fun ItemCard(
    item: Item,
    onItemClick: () -> Unit,
    modifier: Modifier = Modifier  // First optional param
) {
    Card(modifier = modifier) { }  // Applied to root
}

// ✗ Avoid
@Composable
fun ItemCard(
    modifier: Modifier = Modifier,  // Before required params
    item: Item
) { }
```

#### Parameter Order
1. Required data parameters
2. Required callbacks (event handlers)
3. `modifier: Modifier = Modifier`
4. Other optional parameters

```kotlin
@Composable
fun UserProfile(
    user: User,                    // 1. Required data
    onEditClick: () -> Unit,       // 2. Required callback
    modifier: Modifier = Modifier, // 3. Modifier
    showBio: Boolean = true        // 4. Other optional
) { }
```

### State and Composition

#### Hoist State to Caller
Reusable composables should be stateless; receive data and emit events.

```kotlin
// ✓ Good - Stateless
@Composable
fun Counter(
    count: Int,
    onIncrement: () -> Unit,
    modifier: Modifier = Modifier
) {
    Button(onClick = onIncrement) {
        Text("Count: $count")
    }
}

// ✗ Avoid - Stateful (not reusable)
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) {
        Text("Count: $count")
    }
}
```

#### Screen/Route Split
- **Route** composable: stateful, gets ViewModel
- **Screen** composable: stateless, receives UI state
- Screen is `@Preview`-able

```kotlin
@Composable
internal fun HomeRoute(
    viewModel: HomeViewModel = hiltViewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    HomeScreen(
        uiState = uiState,
        onAction = viewModel::onAction
    )
}

@Composable
internal fun HomeScreen(
    uiState: HomeUiState,
    onAction: (HomeAction) -> Unit,
    modifier: Modifier = Modifier
) { /* rendering */ }

@Preview
@Composable
private fun HomeScreenPreview() {
    AppTheme {
        HomeScreen(
            uiState = HomeUiState.Success(listOf()),
            onAction = {}
        )
    }
}
```

### Theming and Resources

#### Use Theme Values
Never hardcode colors, typography, or dimensions.

```kotlin
// ✓ Good
Text(
    text = "Hello",
    color = MaterialTheme.colorScheme.onSurface,
    style = MaterialTheme.typography.bodyLarge
)

// ✗ Avoid
Text(
    text = "Hello",
    color = Color(0xFF000000),
    fontSize = 16.sp
)
```

#### Strings in Resources
All user-visible text goes in `strings.xml`.

```kotlin
// ✓ Good
Text(stringResource(R.string.home_title))

// ✗ Avoid
Text("Home")
```

#### Content Descriptions
Every image/icon needs `contentDescription` or explicit `null`.

```kotlin
// ✓ Good
Icon(
    imageVector = Icons.Default.Home,
    contentDescription = stringResource(R.string.home_icon_description)
)

Icon(
    imageVector = Icons.Default.Decorative,
    contentDescription = null  // Decorative, explicitly null
)

// ✗ Avoid
Icon(imageVector = Icons.Default.Home)  // Missing content description
```

## Coroutines and Flow

### Coroutine Dispatchers

#### Inject Dispatchers
Never reference `Dispatchers.IO` directly; inject it.

```kotlin
// ✓ Good
class Repository @Inject constructor(
    @Dispatcher(IO) private val ioDispatcher: CoroutineDispatcher
) {
    suspend fun save() = withContext(ioDispatcher) { }
}

// ✗ Avoid
class Repository @Inject constructor() {
    suspend fun save() = withContext(Dispatchers.IO) { }
}
```

### Flow Collection

#### Use collectAsStateWithLifecycle
In Compose, use `collectAsStateWithLifecycle()`, not `collectAsState()`.

```kotlin
// ✓ Good
val uiState by viewModel.uiState.collectAsStateWithLifecycle()

// ✗ Avoid
val uiState by viewModel.uiState.collectAsState()
```

#### StateFlow Configuration
Use `SharingStarted.WhileSubscribed(5_000)` for UI-consumed StateFlows.

```kotlin
// ✓ Good
val uiState: StateFlow<UiState> = repository.getData()
    .map { it.toUiState() }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = Loading
    )

// ✗ Avoid
.stateIn(viewModelScope, SharingStarted.Eagerly, Loading)  // Leaks
```

### Error Handling

#### Use Result for Operations
Wrap suspend functions that can fail with `Result<T>`.

```kotlin
// ✓ Good
suspend fun refreshItems(): Result<Unit> =
    try {
        val items = api.fetchItems()
        dao.upsertAll(items)
        Result.success(Unit)
    } catch (e: Exception) {
        Result.failure(e)
    }

// Caller
when (val result = repository.refreshItems()) {
    is Result.Success -> showSuccess()
    is Result.Failure -> showError(result.exception)
}
```

#### Catch in Flow Operators
Use `.catch { }` for Flow error handling.

```kotlin
// ✓ Good
val uiState = repository.getItems()
    .map { Success(it) }
    .catch { emit(Error(it.message ?: "Unknown error")) }
    .stateIn(...)
```

## Hilt Dependency Injection

### Module Structure

#### Use @Binds for Interfaces
Use `@Binds` in `internal interface` module.

```kotlin
@Module
@InstallIn(SingletonComponent::class)
internal interface RepositoryModule {
    @Binds
    fun bindItemRepository(impl: ItemRepositoryImpl): ItemRepository
}
```

#### Use @Provides for Construction
Use `@Provides` in `internal object` module.

```kotlin
@Module
@InstallIn(SingletonComponent::class)
internal object DatabaseModule {
    @Provides
    @Singleton
    fun provideDatabase(@ApplicationContext context: Context): AppDatabase =
        Room.databaseBuilder(context, AppDatabase::class.java, "app-db").build()
}
```

### Scoping

#### Application Scope
Use `@Singleton` for app-wide instances.

```kotlin
@Provides
@Singleton
fun provideDatabase(...): Database
```

#### ViewModel Scope
ViewModels are automatically scoped correctly with `@HiltViewModel`.

```kotlin
@HiltViewModel
class HomeViewModel @Inject constructor(...) : ViewModel()
```

## Testing Standards

### Test Naming
- Test classes: `<ClassUnderTest>Test`
- Test functions: `` `when_condition_then_result` `` (backticks allow spaces)

```kotlin
class HomeViewModelTest {
    @Test
    fun `when items loaded then state is success`() { }
    
    @Test
    fun `when loading fails then state is error`() { }
}
```

### Test Doubles
Use hand-written test implementations, not mocking frameworks.

```kotlin
// ✓ Good - Test double
class TestItemRepository : ItemRepository {
    private val items = MutableStateFlow<List<Item>>(emptyList())
    
    override fun observeItems() = items.asStateFlow()
    
    fun emit(newItems: List<Item>) {
        items.value = newItems
    }
}

// ✗ Avoid - Mocking library
@Mock lateinit var repository: ItemRepository
```

### Assertion Style
Use descriptive assertion functions.

```kotlin
// ✓ Good
assertThat(result).isEqualTo(expected)
assertThat(list).hasSize(3)
assertThat(state).isInstanceOf(Success::class.java)

// ✗ Avoid
assertEquals(expected, result)  // Order confusion
assertTrue(list.size == 3)  // Less descriptive
```

## Comments and Documentation

### When to Comment
- **Public APIs:** Document with KDoc
- **Complex algorithms:** Explain the "why"
- **Workarounds:** Explain why the hack exists
- **TODOs:** Include context and ticket number

```kotlin
/**
 * Fetches items from the remote API and updates the local database.
 * 
 * @return Result.success if sync completed, Result.failure if network error
 */
suspend fun refreshItems(): Result<Unit>

// TODO(#123): Remove this workaround when API supports pagination
private fun fetchAllPages() { }
```

### When Not to Comment
- Don't explain **what** code does if it's obvious
- Don't leave commented-out code
- Don't duplicate what the function name says

```kotlin
// ✗ Avoid
// Increments the counter by 1
counter++

// ✗ Avoid
// fun oldImplementation() { }

// ✗ Avoid
/**
 * Gets items from repository
 */
fun getItems() = repository.getItems()
```

## Formatting

### Use ktlint/ktfmt
Let automated formatters handle style. Key points:
- **4 spaces** for indentation (not tabs)
- **120 character** line limit
- No wildcard imports (except Android framework)
- Trailing commas in multi-line parameter/argument lists

Generated projects include `.editorconfig` to enforce this automatically.

### Line Breaking
Break before operators, not after.

```kotlin
// ✓ Good
val result = someLongExpression
    && anotherCondition
    || yetAnother

// ✗ Avoid
val result = someLongExpression &&
    anotherCondition ||
    yetAnother
```

## Anti-Patterns to Avoid

### Don't Use LiveData in New Code
Use `StateFlow` for reactive state.

```kotlin
// ✓ Good
val uiState: StateFlow<UiState>

// ✗ Avoid
val uiState: LiveData<UiState>
```

### Don't Use !! (Bangbang Operator)
Use safe calls or explicit null checks.

```kotlin
// ✓ Good
val length = text?.length ?: 0
requireNotNull(value) { "Value must not be null" }

// ✗ Avoid
val length = text!!.length
```

### Don't Suppress Warnings Without Reason
Only suppress warnings with a comment explaining why.

```kotlin
// ✓ Good - with explanation
@Suppress("UNCHECKED_CAST")  // Type is guaranteed by Room
val result = data as List<Item>

// ✗ Avoid - no explanation
@Suppress("UNCHECKED_CAST")
val result = data as List<Item>
```

### Don't Use Magic Numbers
Extract to named constants.

```kotlin
// ✓ Good
private const val CACHE_DURATION_MS = 5_000L
WhileSubscribed(CACHE_DURATION_MS)

// ✗ Avoid
WhileSubscribed(5_000)
```

## Summary Checklist

When writing or reviewing code, verify:
- [ ] Proper naming conventions (PascalCase classes, camelCase functions)
- [ ] Correct visibility (default to `internal` in feature modules)
- [ ] Composable follows `modifier` parameter pattern
- [ ] Dispatchers are injected, not hardcoded
- [ ] Flow collection uses `collectAsStateWithLifecycle()`
- [ ] UI state is sealed interface with exhaustive cases
- [ ] No direct DAO/API calls from ViewModels
- [ ] Test doubles are hand-written interfaces
- [ ] All strings in `strings.xml`
- [ ] Content descriptions on all images/icons
- [ ] No `!!` (bangbang) operators
- [ ] No magic numbers
